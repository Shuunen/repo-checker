# Architecture

Status: built, every check of [checks.md](checks.md) is built. The scan, the checks (the ported file checks, the Sync checks, the git state of each clone, the GitHub presentation and activity, the npm registry), the CLI report, the HTTP server, the web app (list, project view and live watch), every action (see Actions) and the file fixes exist, and the old code is removed.

## Shape

One package, one `package.json`, three folders.

```
src/
  server/   Node 26 + TypeScript: scanning, git and gh calls, Hono HTTP server, CLI entry
  shared/   Types and pure helpers used by both sides (Project, ActionKind, plural...)
  web/      React 19 + TypeScript + Tailwind 4 + HeroUI, built by Vite
```

`web/` is built to static files that ship inside the npm package. `repo-check ui` starts the server, which serves those files and the API, then opens the browser. The server serves `dist/web`, prints its URL and opens it in the default browser (`http/open-browser.ts` spawns `xdg-open`, `open` or `cmd /c start`, without a shell and without waiting, and an error to start it is ignored since the URL is printed), `--no-open` keeps the browser closed. It also answers `/project/*` with the page, so a reload on a project address works (any other unknown path is a 404).

```
repo-check ui
   |
   v
Hono server (127.0.0.1)  <----  React app (static files)
   |   \
   |    gh api ...        (GitHub: repos, forks, archive, delete)
   |
   git ...                (local: status, branches, stash, clone)
```

## Rules

- `shared/` imports nothing from `server/` or `web/`. `web/` never imports from `server/`: it reads the events through the types of `shared/scan-event.ts`.
- The server is the only place that runs `git` and `gh`. The browser never talks to GitHub. The one other program it starts is `claude`, for the Update project action (`actions/update/claude-process.ts`, a fixed binary and an argument array, `--permission-prompts none`, `AskUserQuestion` disabled), always in the clone of a project, and every session is stopped when the server stops or restarts.
- All shell calls go through one small wrapper (fixed binary, argument array, never a shell string), so user data can never become shell syntax.
- The scan engine has no HTTP in it. The CLI and the server are two thin callers of the same functions.

## Scan flow

1. Resolve the target: a git repo means single-project mode, a folder of repos means folder mode.
2. Resolve the owner: `--owner` first. Otherwise, in single-project mode the owner of the project's `origin`, in folder mode the `gh` login (`gh api user`).
3. Build the local inventory (git state commands without a fetch, run in parallel, bounded) and the GitHub inventory (`gh api`, paginated). Each usable clone is fetched and read again right before its own check.
4. Match by `origin`, run the project rules on every project and the file rules on usable clones of the owner, and hand each project's result to `onProject` as soon as its checks finish. A project whose checks throw (a malformed file, a gh failure on one fork) does not fail the scan: it gets one `checks-failed` error finding with the message, the others carry on. A fork is compared with its parent right before its own check, so the other projects do not wait for the forks. `onProgress` receives a short line at each step.

The inventory lives in `src/server/inventory`: `shell.ts` (the only place that runs `git` and `gh`), `git.ts` (one `LocalClone` per folder: origin, branches with ahead, behind and gone upstreams, changed files, stash, unpushed commit subjects, local-only branches), `github.ts` (`gh api --paginate --slurp`, private repos included when the owner is the `gh` login, and one search call `search/issues?q=user:owner+is:pr+is:open` for the open pull requests of the whole account, Renovate's apart from the others: in folder mode only, and a failed search, its rate limit is low, leaves them unread and the checks that need them do not apply) and `match.ts` (one `Project` per clone and per repo without clone, other owners flagged). `forks.ts` reads each fork's `ForkStatus` during the scan, right before the fork's check: the parent, every branch compared with the parent's default branch, the open pull requests from each branch, and every failed call. A single failure makes the fork "cannot verify". On 2026-10-12 the 30 forks (120 branches, 2 calls per branch) took about 7 seconds with 8 forks at a time in a pool (13 seconds with 4, 7.8 with 8 in fixed batches), the slowest part of the scan, which is why results stream per project. The types are in `src/shared/project.ts`. A clone whose origin points to the owner but matches no repo keeps `github` undefined: that is the "origin 404" case of `broken-clone`.

The CLI is `src/cli.ts` (the entry point) and `src/server/cli/run-cli.ts` (`inventory/scan.ts` reads the inventory and `inventory/check-projects.ts` checks each project, `cli/report.ts` groups the findings by severity, then prints a summary line: checks run and skipped, counts per severity). `--verbose` also lists every passed and skipped check per project, and progress lines go to stderr so they never mix with the report. It runs as `repo-check` from the built package (`dist/cli.js`, built by `tsdown` with one file per rule) and as `pnpm start` from the sources (`--target`, `--owner`, `--no-fetch`, `--verbose`, a leading `~` in the target is expanded).

`repo-check ui` (`pnpm start:ui` from the sources, `--port`, 4747 by default) starts the server: `serve.ts` listens on `127.0.0.1` with `@hono/node-server`, and `app.ts` is the Hono app. `GET /api/scan` streams the same `scan` as server-sent events (Hono's `streamSSE`), one per `ScanEvent` of `src/shared/scan-event.ts`, its `type` as the event name: `progress` (a line), `project` (one checked project), then `done` (owner, single project mode, duration) or `failed` (the error message). Writes are queued so events keep their order. A finding's edits are functions, so `toScanProject` sends the files they change (`fixFiles`) instead, and the edits stay on the server. Fields that are `undefined`, like `github` of a project without repo, are missing in the JSON. The target and the owner are fixed when the server starts; `?nitpick=true|false` sets the nitpick mode (`started` tells the page which one runs, a scan that changes it checks every project again), `?fetch=false` skips git fetch, and `--no-fetch` wins over the page. A middleware refuses any `Host` other than `127.0.0.1` and `localhost` (DNS rebinding). The page writes those events into a TanStack Query cache, so rows appear one by one, see Web app.

`check-projects.ts` checks the matched projects in two pools that run together: the projects that are not forks, 8 at a time, and the forks, 8 at a time, each compared with its parent (`addForkStatus`) right before its check. The fork comparison is the slowest part of a scan, so the other projects no longer wait for it. Measured on 2026-10-12 on the real data (107 projects, 30 forks), without fetch: first project at 1.4 s, 75 projects by 1.6 s, the last fork at 8.3 s (before, every project came in one burst after 8 to 13 s). Each usable clone is also read again with a fresh `git fetch` right before its own check (`refresh` in `check-projects.ts`, in the same pool, so no project waits for the fetch of another), instead of every clone being fetched before anything is checked. Measured on 2026-10-13 with fetch on the same data: first project at 1.5 s (5.3 s when every clone was fetched first), the 75th at 4.7 s, done at 8.8 s (11.7 s before).

## Web app

`src/web` is a React 19 page built by Vite (`vite build`, root `src/web`, output `dist/web`, which `repo-check ui` serves). `pnpm dev` runs the Vite dev server with `/api` proxied to `pnpm start:ui` on port 4747. Its packages are devDependencies on purpose: Vite bundles them, users never install them.

- The scan stream (in `dashboard/`): `read-events.ts` reads the server-sent events of the response body as they arrive (an event split across chunks is read once complete), `scan-state.ts` folds the events into a `ScanState` (target, last progress line, projects in arrival order, done or failure), and `scan-query.ts` is one TanStack Query `streamedQuery` that opens `/api/scan` and applies that reducer. A refetch (the Rescan button) starts from an empty state. TanStack Query holds the stream now, and will hold the actions of the next steps too.
- The pure logic (in `dashboard/`, `project/`, `actions/`): pure logic, no React. `rows.ts` turns a project result into a table row (pills, branch, last push, the first action it offers) and sorts the worst first, then by name. `filters.ts` has the filter tabs (overview, needs attention, not cloned, forks, archived) and the four summary tiles. A Sync finding gets a short pill label from `ruleId.messageId`, with the full message on hover, and an unknown one falls back on its rule id.
- `project/detail.ts` is the logic of the project view, no React: the identity badges and GitHub link, the fact cards (`localFacts`: path, branch, upstream, unpushed commits, uncommitted files, stashes, local-only branches, or why the folder cannot be compared; `forkFacts`: parent, branches ahead, open pull requests, every failure), the findings grouped by origin (Sync with GitHub, then project files, the worst first) and the distinct actions offered.
- Routing is wouter with path addresses: `/` is the list, `/project/:name` the project view (`routes.tsx`). The name cell of a row links to it, and picking a sidebar filter goes back to the list (`use-filter.ts`). When the scan is of a single project, `use-open-single-project.ts` opens its view once, so the back link still works. A project the scan does not have yet says it is looking for it, then that it is not in the scan.
- The components (`app/`, `dashboard/`, `project/`, `actions/` with one folder per action): one component per file, each under the 30 lines of `max-lines-per-function` (HeroUI v3: Table, Chip, Card, Button, Alert, AlertDialog, Spinner). A piece gets its own file only when it is reused or owns state: for example `dashboard` (query), `routes`, `filter-tabs`, `page`, `scan-body`, `scan-failure`, `health-bar`, `project-table` and `project-row` (the cells are inline), `project-page` (back link, and the project or why it is missing), `project-detail`, `project-identity`, `findings-card` and `finding-item`, `facts-card`, `actions-card` and `action-button`, one `<action>-button.tsx` per action, in the folder of its group (`archive/`, `clone/`, `delete/`, `fix/`, `github-settings/`, `sync-github-metadata/`, `update/`), that holds its button and its dialog, and the hooks `use-filter`, `use-open-single-project` and `use-action-dialog`. The project view has a Fixes card (when a finding has a fix) with a Fix the files button that opens a diff per file (`file-diff.tsx`, from `diff-lines.ts`, which uses the `diff` library), the files whose uncommitted changes get the fix merged in, an optional commit, and Apply the fixes. The row's first action has its own button there, which opens the confirmation from the list.
- `app/follow-system-theme.ts` follows the OS theme by toggling the `dark` class that HeroUI reads.
- Tests: `fixtures.ts` builds findings, projects and a server-sent events response, and `app.test.tsx` renders the whole app against a fake scan request. The web tests run in happy-dom, the server tests in node (two vitest projects in `vitest.config.mts`). `main.tsx` only starts the page and is excluded from coverage.

## Checks engine

Every check in [checks.md](checks.md), Sync checks and ported file checks alike, is one rule run by the same engine. The rule shape copies ESLint and oxlint rules (`defineRule`, `meta`, `context.report`), but the engine is ours: oxlint only reads JS and TS files, and most checks read JSON, YAML, dotfiles, git state or GitHub.

```ts
export const scriptsNoNpmRun = defineRule({
  check({ pkg, report }) {
    const scripts = Object.entries(pkg?.scripts ?? {}).filter(([, script]) => npmRun.test(script))
    for (const [name] of scripts) report({ data: { name }, fix: fixer => fixer.json('package.json').update(['scripts', name], current => toPnpm(String(current))), messageId: 'found' })
  },
  meta: { fixable: true, id: 'scripts-no-npm-run', messages: { found: 'script "{{name}}" uses npm run, use pnpm instead, it is faster' }, severity: 'warning' },
})
```

- `meta.id` is the check id from [checks.md](checks.md). `src/server/engine/rules.test.ts` fails when a rule is not marked ✅ there, or when a check marked ✅ has no rule, so the doc always says what is built.
- `meta.severity` is the only severity, no "just warn" flag at the call site.
- `meta.fixable` must be true for a rule to report a fix, and a `messageId` must exist in `meta.messages`. The runner throws otherwise.
- `context` is built once per project: parsed files (`pkg`, `readme`), project flags, cached file readers (`files.readText`, `files.sizeKo`, `files.search` to find text across the project, skipping `node_modules`, `.git`, `dist` and `coverage`). Git state and GitHub data are not in it: project rules receive the whole `Project` instead. Flags (`engine/flags.ts`) are detected from `package.json` and the `origin` of the git config (owner, repo), then overridden by the project's `.repo-checker.json` (`license`, `maxSizeKo`, `webUrl`...). `webUrl` is the url of the deployed website, not the `homepage` of the `package.json`, which is the repo. Rules never touch the disk, run commands or log.
- A rule that applies only sometimes says so with `appliesTo(context)`, so the runner can tell "skipped" from "passed".
- `src/server/rules` has no file at its root, only group folders (one per group of [checks.md](checks.md)). Inside them, a file is `*.rule.ts` (exports rules), `*.utils.ts` (helpers for the rules of that folder, such as factories) or `*.test.ts`. Anything generic goes to `src/server/engine`. There is no list of rules to maintain: `loadRules(folder)` imports every `*.rule.ts` (sorted by path) and keeps every exported rule, alone or in an array. The server build must therefore emit each rule file as its own module (for example a tsdown entry per `*.rule.ts`), since a bundle would hide them from the loader. `src/server/engine/rules.test.ts` enforces this layout, and fails when a `*.utils.ts` file exports a rule the loader would skip.
- Rules with the same pattern (forbid a dependency, require a property...) come from small factories in the `*.utils.ts` of their folder and are listed as tables, one rule per line. Unusual rules are written out by hand.
- Rules come in two flavors. File rules (`defineRule`) see `files`, `pkg` and `flags` and only run on usable clones. Project rules (`defineProjectRule`, `meta.scope: 'project'`, the `sync/` folder, `git-hygiene/clone-state.rule.ts`, the checks on the git state of a clone: behind-remote, uncommitted-files, unpushed-commits, forgotten-stash, branch-without-upstream, not-on-default-branch, `presentation/github-metadata.rule.ts`, how an own repo presents itself on GitHub: missing-license, missing-description, missing-topics, missing-homepage, made by the `requireRepoField` factory, and `github-health/pull-requests.rule.ts`: open-pull-requests, open-issues) see the whole `Project`, cloned or not, and report actions (`archive`, `checkout-default`, `clone`, `delete-clone`, `delete-fork`, `discard`, `fix-github-settings`, `sync-github-metadata`, `unarchive-push`, the `ActionKind` of `src/shared/action.ts`) instead of edits. An action is only a name in the finding: the server runs it after confirmation, with its own fetch and safety re-check. `splitRules` separates the two flavors, `checkProjectRules` runs project rules, `testProjectRule` tests them from partial clone and repo fixtures.
- A fixer never writes. It returns edits (`fixer.json(file).set/update/remove`, `fixer.text(file, transform)`), each applied on the latest text of its file so edits chain. JSON edits go through `jsonc-parser`, so indentation, line endings, key order and comments are kept.
- The runner works in phases: `checkProject` (findings and one outcome per rule, passed, failed or skipped, nothing written), `planFixes` (one before/after per file, for the confirm dialog), then `fixProject` asks `confirm(plans)`, writes, and checks again to prove the fixes worked.
- Tests are ESLint style: `testRule(rule, { valid, invalid })` with plain objects and in-memory files. An invalid case lists its message ids and, when the rule can fix it, the expected file after the fix: a `package.json` object, or the raw text of another file such as the README. Project rules use `testProjectRule` the same way.
- The boundary is enforced: the oxlint rule `no-restricted-imports`, set in `.oxlintrc.json` for `src/server/engine`, fails `check` when a file there imports from `src/server/rules`.

```ts
testRule(scriptsNoNpmRun, {
  invalid: [{ errors: ['found'], name: 'one script', output: { scripts: { check: 'pnpm lint' } }, pkg: { scripts: { check: 'npm run lint' } } }],
  valid: [{ name: 'pnpm scripts', pkg: { scripts: { check: 'pnpm lint' } } }],
})
```

## Actions

An action is a function in `src/server/actions` that takes the repo name and proves again, right before acting, that the scan was right, then acts, and returns an `ActionResult` (`src/shared/action.ts`): `{ ok: true, message }`, or `{ ok: false, reason }` with the reason to show. A refusal is a normal answer, not an exception. `actions.ts` builds them for a server started on a folder (the owner is the `--owner` option, or the gh login read when an action runs), and `app-actions.ts` routes them: status 200 when it worked, 409 with the reason when it was refused or failed. The routes are built from `postedActions` in `shared/action.ts`, the one list of the actions with their toast and whether they have a preview and a fingerprint, so a route cannot be forgotten. A name that is not a plain repo name (letters, digits, `.`, `-`, `_`, never a path, `.` or `..`) is refused once, by a middleware on `/api/projects/:name/*`, and `options(name)` in `actions.ts` checks it again before any action runs. An action finds its clone with `findCloneOf` or `requireCloneOf` (`guards.ts`), which only read the origin of the other clones (`listClones`), not their whole git state.

- **Request guard**: every request that is not a GET must carry the header `x-repo-check: 1`, otherwise it is a 403. A web page of another site can post to `127.0.0.1` (the host is allowed), but it cannot add a custom header without a preflight request, which the server never answers. The `Host` check against DNS rebinding applies to every request too. The page's `actions/api/post-action.ts` adds the header.
- **Clone** (`actions/clone/clone.ts`): refuses a target that is itself a git repo (single project mode), a folder of that name that already exists, a repo that is gone from GitHub, was renamed, is archived or is a fork (the `not-cloned` rule only offers non-archived non-forks). Then it runs `git clone git@github.com:owner/name.git target/name`, always over SSH like the existing clones (decided 2026-10-13, it needs an SSH key known to GitHub), and the tool never sees a token. A failed clone gives the git error as the reason.
- **Delete clone** (`actions/delete/delete-clone.ts`, the proof in `archive/archived-proof.ts`, shared with Unarchive and push): `proveArchived(options, action)` trusts nothing the page said. It refuses a single-project target, a repo that is gone, renamed, not archived or a fork, no clone or several clones of the repo in the folder, then reads the one clone again with a fresh `git fetch` and runs the Sync rules `archived-with-unsaved-work` and `archived-clone` on it: the action goes ahead only if a rule still offers it (`archived-clone` for `delete-clone`). Otherwise the reason is the message of the rule that fired (for example "1 unpushed commit"), so there is one source of truth for "safe". `previewDeleteClone` (a GET, a few seconds because of the fetch) adds the files git ignores that the delete would lose: `git ls-files --others --ignored --directory`, leaving out the folders a build recreates (`node_modules`, `dist`, `coverage`, `.cache`, `.turbo`), and a folder git collapsed is only listed when it holds a real file (read one folder at a time, stopping at the first file, so a big `.venv/` stays fast). `deleteClone` (a POST) runs the proof again, then `removeClone` (`delete/remove-clone.ts`, shared by every delete) checks the clone is a direct child of the folder of projects and removes the folder with `fs.rm`. It never touches GitHub. The folder is removed for good, not moved to a trash: what is lost is only what the dialog listed.
- **Unarchive and push** (`actions/archive/unarchive-push.ts`): the same proof, for the action `unarchive-push` (so `archived-with-unsaved-work` must still offer it on the freshly fetched clone), then three more refusals: uncommitted files or a stash, because it only pushes and never creates a commit, and commits of a detached HEAD, which are on no branch to push. It then runs `gh api --method PATCH repos/owner/name -F archived=false`, pushes in one `git push --atomic origin refs/heads/b:refs/heads/<upstream of b> …` (every branch with unpushed commits to its upstream branch, every local-only branch to a branch of its name, all or none, never forced), and always archives the repo again, whether the push worked or not, then reads the repo back from GitHub to be sure it is archived (a call that says ok but did nothing, or a repo that cannot be read, gives the hand command too). A failed unarchive pushes nothing. A failed push says the repo is archived again and nothing was pushed. If archiving again fails, the reason gives the hand command (`gh api --method PATCH repos/owner/name -F archived=true`), since the repo is left writable. The scanned data already holds the unsaved items, so the page lists them without asking the server.
- **Discard** (`actions/delete/discard.ts`): the same proof, for the action `discard`, then a plan of git steps built from the freshly fetched clone and run in order, stopping at the first failure (the reason then says the clone may be half discarded): `git stash clear`; when the checked out branch has no upstream on GitHub (local-only, gone upstream, detached), `git checkout --force` to the default branch of GitHub (`origin/HEAD`), or else the first branch that has an upstream, and a refusal when no branch exists on GitHub; `git branch --force b upstream` for every other branch that is ahead; `git reset --hard upstream` on the landing branch; `git clean -fd` (uncommitted and untracked files, the ignored ones stay); `git branch -D` for every local-only branch. It then reads the clone again and reports anything still unsaved. What the user confirms is exactly what is thrown away: the preview (a GET, a few seconds because of the fetch) returns the list (`shared/unsaved.ts`) with a SHA-256 fingerprint of it, the page sends that fingerprint with the POST, and the discard re-reads the clone fresh and refuses when its list no longer gives the same fingerprint (a file added after the dialog was read, for example). Nothing is touched on GitHub.
- **Delete fork** (`actions/delete/delete-fork.ts`, the proof in `delete/fork-proof.ts`): `proveFork` trusts nothing the page said. It refuses a single-project target, a repo that is gone, renamed or not a fork. It then reads the fork's status again from GitHub (`readForkStatus`: the parent, every branch compared with the parent's default branch, the open pull requests from each branch, every failed call), reads its clone if it has one again with a fresh `git fetch` (several clones are refused), and runs the strict Sync rule `pristine-fork` on that fresh data: the delete goes ahead only if the rule still offers `delete-fork`, so the reason of a refusal is the rule's own message (a branch is 2 ahead, an open pull request, a comparison that failed is "cannot verify", the clone has an unpushed commit). The last proof is the token: `delete-scope.ts` reads the `X-OAuth-Scopes` header of `gh api -i user` and refuses with `gh auth refresh -s delete_repo` when the scope is missing (a token that sends no such header, a fine-grained token, is tried, and a 403 from GitHub gives the same command). `deleteFork` checks the clone path first (a clone that is not a direct child of the folder of projects stops it before GitHub is touched), then deletes on GitHub with `gh api --method DELETE repos/owner/name` (`deleteRepoOnGithub` of `delete/remove-clone.ts`, which checks the scope again), so a refusal leaves the clone alone, and only then removes the clean clone. `previewDeleteFork` (a GET) says the parent, how many branches were compared, and the clone that goes too with the ignored files in it.
- **Rescan** (`actions/rescan.ts`): after an action succeeded, `GET /api/projects/:name/rescan` scans only that project again: its repo from GitHub, its clone found by the repo it points to (or by its folder name for a broken one) and read with a fresh fetch, then the same checks as the scan (`checkProjects` on one project, so a fork gets its comparison). It answers `{ ok: true, project }` with the project as it is now, `{ ok: true }` without a project when it is gone (a deleted fork, a repo that does not exist and has no folder), or a refusal. It takes about 1 to 2.5 s on the real data, against about 12 s for the whole list. `project/refresh-project.ts` puts the answer in the TanStack Query cache in place of the old entry (`replaceProject`), so the rest of the list stays and nothing blanks. When the project cannot be scanned alone (a refusal, an answer that is not JSON, a server that cannot be reached) the whole scan runs again.
- **Fix files** (`actions/fix/fix-files.ts`, the plan in `fix/fix-plan.ts`): built on the engine's `planFixes` (a before and after per file), and the same code as the CLI `--fix`. The server finds the clone (the target itself in single project mode, or one of its folders: a usable clone of the owner, like the scan), runs the file checks on the files as they are now and plans every fix, creating the new files and the folders they need. A file that git reports as changed (`git status`: modified, untracked, renamed) gets the fix merged into its changes and is listed in `merged`. The preview (a GET) returns the plans, the dev dependencies to install, the description to set on GitHub, and a SHA-256 fingerprint of all that; the page sends the fingerprint back with the POST, and the server plans again from scratch and refuses unless it is identical (a file edited meanwhile, for example), then writes the files, installs, and checks again to say what is left. With `commit=true` the answer streams its stages (writing, installing, checking, committing, pushing, `fix/fix-commit.ts`): only the files it wrote are committed, after the check of the project passes, never a file with your own changes. `diskIo.writeText` creates the folders and refuses any path that leaves the project, through `..` or through a symbolic link (the real path of the folder is checked, and a file that is itself a link is refused).
- **Delete project** (`actions/delete/delete-project.ts`): the trash icon of any project. It refuses a single-project target and a renamed repo, finds the repo of the owner on GitHub and its clone (by origin, or by folder name only for a folder with no GitHub origin), refuses several clones and a clone that is not a direct child of the folder of projects. The preview lists the repo and, for the clone, its unsaved work (`delete/unsaved-summary.ts`: unpushed commits, a detached HEAD included, changed files, stashes, local-only branches, or "everything" for a folder with no origin, no git or an unreadable state) and its ignored files, with a fingerprint of that list; the POST reads everything again and refuses unless the fingerprint is the same, then deletes the repo on GitHub first and the clone after.
- **Delete branches** and **Fix git** (`actions/delete/delete-branches.ts`, `actions/fix/fix-git.ts`, the proof `proveClone` with a fresh fetch): delete every local branch but the default and the checked out one, or apply the git plan (pull fast forward only, move the other branches forward, drop the stashes, delete the local-only and merged branches). Their fingerprint covers the list and the commit each branch points to, so a commit made after the preview stops them.
- **Checkout default** (`actions/clone/checkout-default.ts`), **Archive and Unarchive** (`actions/archive/archive.ts`), **Fix the GitHub settings** (`actions/github-settings/`) and **Sync infos** (`actions/sync-github-metadata/`): each proves the repo again on GitHub first. Checkout refuses uncommitted files and the commits of a detached HEAD, which it would orphan. Fixes are applied for the whole project at once, per finding is a possible refinement.
- **Page**: the project view's Clone button opens a confirmation (HeroUI AlertDialog) that says what will be cloned and where, and nothing is sent before Clone is pressed. On success the project is scanned again alone and replaced in the list, and the dialog closes. A refusal stays in the dialog, with its reason. The Delete clone button opens a dialog that first asks the server for the preview ("Checking again, with a fresh git fetch…"), then shows the folder and the ignored files that would be lost (the first 20, and how many in all), or the reason the delete is refused. Delete is disabled until the proof holds, and the delete proves everything again when it is confirmed. The Unarchive & push button opens a dialog that lists the unsaved commits, branches, files and stashes (`unsaved-list.tsx`, shared with the next dialogs), says the repo is writable for a few seconds, and shows why it cannot run, with the confirm button disabled, while the clone has uncommitted files or a stash. The Discard dialog reads the list when it opens ("Reading again, with a fresh git fetch, exactly what would be thrown away…"), shows every item, says there is no undo and that ignored files stay, and sends the fingerprint with the confirmation. The first action a project offers has its button right in the row of the list (the same `ActionButton` and the same dialogs as on the project page, decided in the review on 2026-10-13), so a confirmation can start from either place. The Delete fork dialog first checks again ("…comparing every branch with the parent, the open pull requests and your gh token…"), then says the fork is deleted on GitHub for good, how many branches were compared, and the clean clone that is deleted too with its ignored files, or the reason it is refused, such as the missing scope with its command. Every action has one `useActionDialog` (`use-action-dialog.ts`): it asks for the preview when `postedActions` (`shared/action.ts`) says the action has one, sends back its fingerprint when it has one, and gives a single `dialog` object. Every dialog is one `ConfirmDialog` fed by that object (heading, what it says, Cancel, confirm, the test ids start with a prefix), and the body of a previewed action is a `PreviewBody`, which shows the checking, refused and error states with the same prefix. An action chosen in the Actions menu mounts its button inside `OpensAtOnce`, so its dialog opens at once and the button is not shown.

## Live watch and cache

The scan is split by what costs something. The **local side** of a project (its files and its git state) is cheap to read and costs no GitHub call. The **remote side** (the repo and its pull requests from GitHub, the `git fetch`, the fork comparison) is slow and spends the rate limit. Both the cache and the watch of the open project follow that split.

- **Fingerprint** (`inventory/fingerprint.ts`): `fingerprintFolder` hashes `git status --porcelain=v1 -z --branch --untracked-files=all`, `git for-each-ref` of the local branches, the remote ones and the stash, the sha of HEAD, and the modification time and size of each changed file, run with `--no-optional-locks` so it never fights the index lock of an IDE. The `stat` of the changed files is needed because `git status` prints the same line the second time a modified file is edited. It takes 4 to 8 ms. Files git ignores are not in it, and `search` of `engine/io.ts` lists files with `git ls-files --cached --others --exclude-standard` (the disk walk is only the fallback without git) so what a rule reads is what the fingerprint sees. Nothing is fetched, so GitHub is not in it.
- **Memory** (`project-memory.ts`): in the memory of the server, per project name, the last `ProjectResult`, the fingerprint taken _before_ it was checked, and when its GitHub side was read. The key has no rules version because the memory dies with the process and the rules only change when it restarts; a persisted cache would have to add the version of the tool, a hash of the rule files and the global facts (Node LTS, git user). A result is reused (`recall`) when the fingerprint is the same and the GitHub side is younger than 5 minutes (`remoteTtlMs`).
- **Ignored rules** (`ignored-rules.ts`): hovering a finding on the project page shows "Ignore for 24h", which posts `POST /api/projects/:name/ignore-rule?rule=<id>`. The server keeps `{ project: { ruleId: expiresAtMs } }` in `$XDG_STATE_HOME/repo-checker/ignored-rules.json` (default `~/.local/state/repo-checker/`), loaded when the server starts and written at once on every change to a temporary file then renamed, so a crash or restart never loses or half writes it. Expired entries are dropped when it loads and when it saves. The filter is applied where a result becomes a page payload (`toScanProject`), not in the memory of results, so it takes effect at once and ends by itself after 24 hours: the findings of the rule are left out and its outcome is `skipped`. A project opened again after the 24 hours shows the finding at its next scan.
- **Scan**: `checkProjects` asks the memory before each project, so refreshing the page only checks what changed, a project reused skips its fetch, its fork comparison and its rules. `GET /api/scan?fresh=true` (the Rescan button, or the fallback of a failed rescan, see `askFreshScan`) checks everything again, still remembering the results. Results with a `checks-failed` finding are never remembered.
- **Watch** (`actions/live.ts`, `GET /api/projects/:name/live?since=<fingerprint>`): the project page asks every 3 seconds (`pollMs`, `use-live-project.ts`). Nothing is sent while the tab is hidden or a dialog is open, and an answer that arrives once a dialog opened is dropped, so a preview is never replaced under the user, and a fix still proves its own fingerprint on the server. The server answers `{ changed: false }` for 7 ms of git while nothing changed. When the clone changed it reads the clone again _without fetch_ and runs every rule on it with the GitHub data it already had (rules are pure functions of the project and its files, so there is no local/remote split of the rules, only of the data), and sends the project, which replaces its entry in place (`putProject`). Only once the GitHub side is older than the time to live does it scan the project alone (`rescanResult`: repo, fetch, fork comparison), unless `gh api rate_limit` (free) says fewer than 300 calls are left: then the answer says `remote: 'paused'`, the page says so, and the rate limit is looked at again a minute later. The pull request counts only a full scan gives are kept from the memory when a project alone is scanned.
- **Owner**: `createActions` asks `gh api user` once and keeps the login. It used to ask on every action, which at one poll every 3 seconds would have spent about 1200 calls an hour.

## Testing

- Scan engine: unit tests against throwaway git repos created in a temp folder (clean, dirty, ahead, stash, local-only branch). `gh` is replaced by a fake that returns recorded JSON.
- Safety rules: one test per rule in `docs/features.md`, including the refusal paths.
- Web: vitest in happy-dom with Testing Library, `getByTestId` only, against a fake scan response (a real stream of server-sent events, cut in small chunks too).
- A real-`gh` smoke test is manual and read-only.

## Build

During development Node 26 runs the TypeScript sources directly. For the npm package, Vite builds `src/web` and `tsdown` builds `src/server` to plain JavaScript, because Node does not strip types inside `node_modules`: users only need Node 26, not a package manager. Both outputs ship in the npm package.

## Distribution

Published to npm as `repo-check` (see `docs/designs/projects-dashboard.md`). Needs `git` and an authenticated `gh`.
