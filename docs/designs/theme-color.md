## Problem Statement

Three places hold "the project color" and drift apart. In this very repo the manifest `theme_color`/`background_color` and the `<meta name="theme-color">` are `#024eb8`, while `.vscode/settings.json` `workbench.colorCustomizations` is slate `#232F3A`. Today `vscode-colors` only asks for any non-empty customizations, and the hash of the project name is used as a color when nothing exists. Goal: one detected `themeColor`, overridable in `.repo-checker.json`, that drives every place so things are aligned.

## What Makes This Cool

Set one color once and the web manifest, the meta tag, the splash screen and the editor window all follow it. Drift becomes a reported, fixable issue instead of something noticed by eye.

## Constraints

- 100% coverage + lint (`pnpm check`) before commit, rules are small and tested.
- No random/hash colors anywhere. repo-checker must never invent a color.
- Existing check ids and docs/checks.md stay the reference.

## Premises (all confirmed)

1. `themeColor` is a detected value (a flag, like `isWebPublished`). Sources by priority: `.repo-checker.json` `themeColor`, manifest `theme_color`, `index.html` meta `theme-color`, VS Code `titleBar.activeBackground`. First found wins.
2. Nothing found: a new check `theme-color-missing` says where to define it (the 4 places). No auto-fix, no default color. This also removes the hash in `vscode-colors` and the `#ffffff` defaults in `manifest-required-fields` and `index-html-theme-color`.
3. Derived values, HSL, same hue and saturation: `titleBar.activeBackground` = themeColor. A darker shade (lightness minus 16 points, floor 0) feeds both `activityBar.background` and manifest `background_color`. `titleBar.activeForeground` = near-white or near-black, whichever contrasts better. No separate backgroundColor setting (user decision: background is inferred from themeColor).
4. Any place that differs from the winner is reported as drift. The fix rewrites only that value; other `colorCustomizations` keys are kept. Colors are compared normalized (`#FFF` = `#ffffff`, case-insensitive).
5. `themeColor` is added to `schema.json` as an optional hex string, and `docs/checks.md` documents the new/changed checks.

## Decisions and why

- Detection order (D2/D5): respect colors already chosen on the web side, the editor is the last source.
- background_color (D3): user chose inference from themeColor, same darker shade as the activity bar, over an independent override.
- Hash fallback (D4): rejected by the user, replaced by an explicit issue. Ruled out: always-enforce hash (mass repaint).
- Derivation (D6): lightness minus 16, first minus 8 was too light.

## Approaches Considered

- A: minimal, helper file, each rule detects itself. Ruled out: detection logic duplicated in 5 rules.
- C: one combined drift rule. Ruled out: loses per-file check ids already in docs.

## Recommended Approach

B: detect `themeColor` once in `src/server/engine/flags.ts` (config override like other flags), rules read `flags.themeColor` and compare. Reuses the HSL helpers in `vscode.rule.ts` (`toHex`) and the manifest/page finders (`findManifest`, `findPages`).

## Decisions from the follow-up interview

- `theme-color-missing` applies to every project with a `package.json`, severity info (as built).
- Manifests are found anywhere git sees them: a file named `manifest.json` or ending in `.webmanifest`, parsed as a json object without `manifest_version` (browser extension). The location does not matter.
- With several manifests, every one is checked and fixed. The theme color comes from the first valid one in path order.
- Every `index.html` page follows the one theme color.
- `msapplication-TileColor` and the `mask-icon` `color` must equal the theme color when the tag already exists, the tags are never added.
- Built in one commit, then this repo's own VS Code colors and manifest `background_color` were fixed by repo-check itself.
