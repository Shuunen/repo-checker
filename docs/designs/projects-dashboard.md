# Design: repo-checker v2, a projects dashboard

## Problem Statement

Shuunen has about 105 repositories on GitHub and 21 local clones in `/home/rominou/Projects/github/`. Nothing tells them when the two sides disagree: a repo that is only on GitHub, an archived repo that still has unpushed local commits, a stale fork. The goal is one entry point to manage all your projects.

Today `repo-check` inspects the files inside one repo (README, biome, workflows). It does not look at all your projects together.

## What Makes This Cool

- Run `repo-check ui` in a folder of projects and watch each project's row fill in live as its check finishes.
- Every fix (clone, delete a clone, delete a fork) sits behind one explicit confirmation, and deletes only appear when the tool can prove nothing is lost.
- The same rule drives the CLI and the UI: run it in one project and you get that project, run it in a folder of projects and you get all of them.

## Constraints

- Personal tool first. No need to be generic, but nothing machine-specific is hardcoded.
- Single package, one `package.json`. Code lives in `src/server`, `src/shared`, `src/web`.
- GitHub access goes through the `gh` CLI. The tool never reads or stores a token.
- The server listens on `127.0.0.1` only, because it can delete things.
- TypeScript, oxlint + oxfmt, vitest (same as the `snippets` repo). bun in development, Node 24 for users.

## Premises

1. The useful v1 is the Sync checks (local vs GitHub). Every other check of `docs/checks.md` is ported into the same engine as well, the old file checks included: the v1 line only says what came first, not what ships (updated 2026-10-12).
2. A browser dashboard fits better than a terminal UI for this data.
3. Reusing the repo name `repo-checker` is right, even though the new tool shares almost no code with the old one.
4. One explicit confirmation is enough safety if the tool refuses to offer a delete unless it has proved it is safe, and re-checks that proof right before acting.

## Decisions

- **Name**: keep `repo-checker`, package `repo-check`, command `repo-check`. Considered and ruled out: `repo-keeper` (three GitHub repos with that name, one almost identical in purpose), `majordome` (taken on npm), `repo-garden` and `repo-tower` (free, but the user preferred to reuse the existing repo). `npx repo-checker` is a different, unrelated npm package: never document it.
- **Rewrite scope**: full rewrite on branch `rewrite/projects-dashboard`. The old code stays untouched until these docs are approved, then is removed in one separate commit. The old snapshot tests are kept in git history as the spec for the future file checks.
- **Release plan**: the old version stays published on npm until the old file checks are ported. The rewrite ships as a new major version.
- **Layout**: one package, `src/server`, `src/shared`, `src/web`. A pnpm workspace of three packages was ruled out as too much config for one user.
- **Modes**: `repo-check` (CLI) and `repo-check ui`. Inside a single project it targets that project, inside a folder of projects it targets all of them. The UI opens on the project view or on the project list accordingly.
- **Server**: Hono with `@hono/node-server`. Typed `hc` client for the web app. Fastify and plain `node:http` were ruled out (heavier, or too much hand-written plumbing).
- **Live results**: the scan streams to the page as each project finishes. A single final JSON response was ruled out (blank page for the whole scan). A background service with notifications is deferred to the TODO list.
- **GitHub access**: shell out to `gh api`. Octokit and raw `fetch` were ruled out because they would put a token in our process.
- **Scan target and owner**: auto-detected from the current folder. `--owner=` wins. Otherwise a single project uses the owner of its `origin`, and a folder of projects uses the `gh` login. Repos whose `origin` belongs to another owner are shown as "other owner" and left out of the comparison.
- **Single source for checks**: `docs/checks.md` lists every check, v1 and later, under its kebab-case id, and the code and tests use the same ids. `docs/features.md` holds the v1 behavior details, `TODOS.md` only the work that is not a check. Letter ids (A1 to A5) were dropped.
- **Severity**: one scale for every check, 🔴 error, 🟡 warning, 🔵 info. Ported checks keep the old tool's level (failed is error, warning is warning). A separate "at risk" or "cleanup" level was ruled out to keep the scale small: the action offered tells those apart.
- **Fetch**: the scan runs `git fetch --prune` on every clone, in parallel, so "unpushed" is measured against the real remote. Each destructive action fetches again before its re-check. Skipping the fetch was ruled out (stale tracking refs can hide unpushed work), and so was asking the GitHub API per commit (too many calls).
- **Fixes**: all fixes are included in v1, deletes too, each behind one explicit confirmation in the UI. The CLI is report-only. See `docs/features.md` for the exact guards.
- **Checks engine**: one engine for every check, rules written in the ESLint rule shape (`defineRule`, `meta`, `context.report`), fixes collected as edits then previewed, applied after confirmation and re-checked. See `docs/architecture.md`. Ruled out: the old `FileBase` class per file (shared mutable state, fixes applied while checking, ids built from messages), a custom oxlint plugin as the engine (oxlint only reads JS and TS files, while most checks read JSON, YAML, dotfiles, git or GitHub), ESLint 9 with JSON and Markdown language plugins (brings ESLint back, still misses YAML, dotfiles and Sync), zod schemas as the rule format (cannot map issues to check ids and severities, no fixes).
- **Server build**: `tsdown`. Web build: Vite.
- **UI library**: HeroUI v3 (installed package, Tailwind 4, React 19). Considered and ruled out: Mantine (second styling system next to Tailwind), shadcn/ui with Tremor (you own and maintain copied code), premade admin templates and admin frameworks such as refine and react-admin (heavy fit for streaming scans and git actions), a terminal UI (replaced by the web UI).
- **Look**: calm and modern, light and dark themes following the OS setting. See `docs/ui.md`.
- **Tooling**: same as `snippets` for oxlint + oxfmt, vitest, Vite for the web build, and its code conventions. See `docs/conventions.md`.
- **Runtime**: bun in development, Node for users (decided 2026-10-12). bun is the package manager and runs the TypeScript sources directly. The published package stays plain JavaScript built by `tsdown`, so `npx repo-check` only needs Node. Ruled out: pnpm with Node everywhere (the user prefers bun to run TypeScript), and publishing for bun only (every user would need bun installed).

## Approaches Considered

### Approach A: Web dashboard served by the CLI (chosen)

`repo-check ui` starts a local Hono server that serves the built React app and streams scan results. Effort: L. Risk: medium (new stack, destructive actions). Reuses: nothing from the old code except the name, the repo and its CI.

### Approach B: Terminal UI

Full-screen list in the terminal, reusing the merge TUI helpers from the `snippets` repo. Ruled out when the user moved to a web stack.

### Approach C: Report-only CLI

Print the report and stop. Smallest build, zero risk, but the fixes are the point of a single entry point. Ruled out.

## Recommended Approach

Approach A, built in this order: scan engine and tests (no UI), CLI report, server with streaming, UI project list, UI project view, then the confirmed actions. See Next Steps.

## Resolved Questions

1. **Archived repo with work that exists nowhere else** (`jozzo`, `c-est-donne`: archived, 1 unpushed commit each). GitHub rejects pushes to an archived repo. The project view shows a dialog that lists the unsaved items and offers two actions: **unarchive, push, re-archive** (one confirmed action, ends where it started with the commits saved on GitHub; it never creates commits, so it is disabled while uncommitted files or a stash exist), or **discard** (reset to the remote state, remove uncommitted and untracked files, drop the stash, delete local-only branches, all in one action, after listing every item). A clean clone then becomes eligible for "delete the local clone". Ruled out: patch export, warn-only, per-category checkboxes.
2. **CLI in v1** is report-only. `repo-check` prints the Sync findings grouped by severity, one green line when all is well, and a hint to run `repo-check ui` to fix. It never prompts. All fixes live in the UI. Fixes with `y/N` in the terminal are in `TODOS.md`.
3. **Local folders that are not usable git repos** (no `.git`, no `origin`, or `origin` returns 404): report only, with the reason and the path. No action, because nothing in such a folder has a remote copy.
4. **"Pristine fork"** is strict, and was checked on the 30 real forks on 2026-10-12. A fork is offered for deletion only when every branch has zero commits ahead of the parent, there is no open PR from the fork, and every comparison succeeded. Anything unprovable is listed as "cannot verify" and never offered. Evidence: 12 forks have zero commits ahead on their default branch, but only 4 of those have no other branch; the others carry branches such as `patch-1`, `feature/i18n` and `pkgjsonfix` that a default-branch-only rule would have deleted. `tina-blog` makes the compare call fail with a 404 ("no common ancestor"), so a failed comparison must never count as "nothing to lose".
5. **Server build**: `tsdown` (0.23.x, active, TypeScript 6 supported, similar to `tsup`). `tsup` last published in November 2025. Publishing raw TypeScript is not possible because Node does not strip types inside `node_modules`.
6. **HeroUI v3** (3.2.6, MIT) peers on React 19 and Tailwind 4 (`>=4.0.0`), built on `react-aria-components`. Its animations are CSS based: components expose `data-entering`, `data-exiting` and `data-pressed` attributes, styles use `tw-animate-css`, `prefers-reduced-motion` is honored. `motion` (Framer Motion) is optional for custom effects.

## Success Criteria

- `repo-check ui` in `/home/rominou/Projects/github` shows the first project rows in about a second and finishes the full scan of 21 local plus 105 remote repos in under about 15 seconds (targets, to be measured).
- It reports the cases found on 2026-10-12: `jozzo` and `c-est-donne` (archived with unpushed commits), `rock-solid`, `finga` and `musiblox` (not cloned), `migrate-to-base` (no git).
- No fork delete is ever offered while its local clone holds unsaved work, and an archived fork is never offered two deletes.
- No delete is ever offered for a clone with uncommitted files, unpushed commits, a stash, or local-only branches, and none for a fork that has any commit ahead of its parent on any branch, an open PR, or a failed comparison.
- On the 2026-10-12 data the strict fork rule offers at most the 4 forks that only have a default branch and zero commits ahead (`The-Documentation-Compendium`, `qbt-theme`, `typescript-run`, `validation-lib-comparison`), and lists `tina-blog` as "cannot verify".
- `repo-check ui` in a single project opens on that project's detail view.

## Distribution Plan

- npm package `repo-check` (unchanged name), new major version once the old file checks are ported. The built web app is bundled inside the package, so `npx repo-check ui` is a single command.
- Requires `git` and an authenticated `gh` CLI on the machine. Deleting forks also needs `gh auth refresh -s delete_repo`, and the UI explains that when the scope is missing.
- CI: the existing GitHub Actions workflow, updated for the new scripts.
