## Problem Statement

Starting the dashboard takes a terminal: run `repo-check ui --target ~/Projects/github`, then use the browser tab it opens. The goal is an icon in the desktop app launcher that opens the dashboard in its own window in one click.

## Constraints

- The dashboard is already an installable PWA (commit `99bfab8`) served on a fixed origin, `http://127.0.0.1:4747` (`defaultPort` in `src/server/http/ui.ts`). Because the origin is stable, the installed PWA keeps working across server restarts.
- A PWA can't start a local process: it runs inside the browser sandbox. The server has to be started outside the PWA.
- The server binds to 127.0.0.1 only, because its actions can delete things. Keep it that way.
- Built for one user on Linux. Other operating systems are out of scope.

## Premises

1. Missing the server is the only gap: the PWA window itself is good enough as the dedicated window.
2. Something outside the browser (a launcher, systemd, a wrapper) has to start the server before the window opens.
3. The server may keep running after the window closes, because the dashboard already has a shutdown button (`shutdown` in `ui.ts`).

## Approaches Considered

- **A. Launcher script that opens the installed PWA:** chosen.
- B1. systemd user service, always on: rejected, because a Node process would idle in the background all day.
- B2. systemd socket activation: rejected for now. It needs `serve.ts` to accept the socket systemd passes and an exit after idle time. It is the upgrade path if A feels clunky.
- C. Electron or Tauri wrapper: rejected. It means 1–2 days of work and a second packaging pipeline for a personal tool.

## Recommended Approach

A `.desktop` entry runs a small launcher script:

1. **Health check:** request `http://127.0.0.1:4747/` and confirm the answer comes from repo-check (for example a known API route), not from some other app on that port.
2. **Start if down:** run `repo-check ui --target ~/Projects/github --no-open` detached, logging to `~/.local/state/repo-check/ui.log`. Poll for up to about 15 s.
3. **Open the window:** run the Exec line of the installed PWA, `<browser> --profile-directory=Default --app-id=<id>`. If the PWA isn't installed, fall back to `<browser> --app=http://127.0.0.1:4747`.
4. If the server never comes up, show `notify-send` with the last log lines. Never leave a silent failure.

The `.desktop` file sets `Icon=` to the PWA icon and `StartupWMClass=crx_<id>`, so the window groups with the PWA in the dock.

Pitfall: a `.desktop` launch doesn't load `.bashrc`, so `node`, the global `repo-check` bin and `gh` may be missing from `PATH`. Use absolute paths or `bash -lc`.

## Open Questions

- Which browser holds the installed PWA (Chrome, Chromium, Brave), and what is its app id?
- Is there a cheap route that proves the server is repo-check, or should one be added (e.g. `GET /api/health` returning the name)?
- Should the PWA ship a service worker fallback page ("server not running") instead of the browser's error page?
- Keep it as a personal script in dotfiles, or ship `repo-check install-launcher` (Linux only, about 2–3 h because of the 100% coverage rule)?

## Success Criteria

- Clicking the launcher icon with no server running opens the dashboard window in under 5 s.
- Clicking it again with the server running focuses or opens the window and doesn't start a second server.
- The window groups under the same dock icon as the PWA.
- A failure to start shows a notification that includes the log tail.

## Distribution Plan

Phase 1: a personal script and `.desktop` file, not shipped. Phase 2, only if it proves useful: a `repo-check install-launcher` command, published to npm by the existing CI.
